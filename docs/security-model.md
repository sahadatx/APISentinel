# Security model and current limits

The API defaults to localhost. TestRun now supports only an explicitly approved, bounded HTTP request mode; this is transport execution, not a vulnerability check. Analyst accounts use Argon2id password hashes and opaque, server-side sessions. Only session-token hashes are persisted; session cookies are HttpOnly, SameSite=Lax and Secure in production. Unsafe cookie-authenticated requests require a CSRF cookie/header pair and an allowlisted Origin. Local user provisioning is CLI-only.

Each client has a nullable analyst owner. New clients are assigned to the authenticated analyst; an owner can add existing analysts as `viewer`, `analyst`, or `reviewer` members. Owners retain full access; viewers are read-only; analysts can make changes and execute authorized requests; reviewers can review authorization, approve endpoints, and triage findings but cannot execute network requests. Membership changes are audited. Legacy ownerless clients remain hidden by default. This is client-scoped RBAC, not a global administrator or user-provisioning system. Accounts can enroll TOTP MFA when the configured secret provider is available (Fernet in development, AWS KMS envelope encryption in staging/production); ten one-time recovery codes are returned once and stored as hashes. Successful MFA sign-ins reject replayed TOTP counters and consume recovery codes. Eight failed password or MFA attempts within 15 minutes lock an account for 15 minutes; successful sign-in clears the counter. Password reset, administrator-driven account lifecycle and session administration remain absent. Production requires HTTPS, Secure cookies and protected database/key backups. Audit events persist in the database, but retention, external export and tamper-evident integrity are not implemented.

An assessment contains authorization reference, allowed hosts, allowed paths, excluded paths, request ceiling, testing window and environment fields. `runner.py` adds a reusable, non-scanning request primitive. It reloads the assessment through an owner or authorized analyst membership, requires recorded authorization, permits only GET/HEAD/OPTIONS, validates scheme/host/path/exclusions and approved ports, resolves all DNS answers within the overall request deadline, and refuses any non-global answer by default. A custom HTTPX/httpcore network backend connects directly to the approved numeric IP using `socket.connect()` without resolving the hostname again, then checks the actual peer socket address; TLS remains verified against the original hostname, preserving SNI and Host behavior. Environment proxies are disabled. Redirects are manual, bounded to three hops, each destination is revalidated, and Authorization/Cookie are removed on origin changes. The runner asks for `Accept-Encoding: identity` and rejects any non-identity `Content-Encoding` before consuming its body, preventing decompression expansion. Accepted bodies are streamed and capped by decoded body bytes; this is not a compressed-entity or TLS/wire-byte limit. Connect/read/write/pool timeouts, database-backed per-assessment rolling request-rate reservations, shared concurrency reservations, an overall request deadline, and TLS verification are explicit. SQLite serializes writers and PostgreSQL uses row locks; reservation storage failure blocks execution instead of falling back to process-local state. Crashed reservations expire after the bounded request deadline plus connection/read grace. Cancellation remains cooperative between chunks and cannot interrupt a socket blocked until its read timeout.

The only private-address exception is an explicit `APISENTINEL_ALLOW_LOCAL_LAB=true` setting in development/lab assessments, restricted to localhost/loopback destinations. Plain HTTP additionally requires `APISENTINEL_RUNNER_LAB_ALLOW_HTTP=true`; non-default ports require an entry in `APISENTINEL_RUNNER_LAB_ALLOWED_PORTS`. These exceptions are rejected in production. Proxy-based routing is not supported; if a future deployment adds a proxy that resolves destinations remotely, this connection pinning guarantee will no longer apply and must be reworked. The transport injects its pinned network backend through HTTPX/httpcore integration internals. Runtime and package constraints are exact (`httpx==0.28.1`, `httpcore==1.0.9`) and startup import fails if either differs; upgrades require the wire-level regression tests to pass before changing the pins. This primitive is not exposed as a general-purpose API endpoint and does not implement vulnerability checks.

An endpoint starts unapproved after OpenAPI import. An authenticated reviewer, analyst, or owner must explicitly approve it through `POST /api/v1/discovery/endpoints/{id}/execution-approval`. Approval requires a current `ACTIVE` authorization record bound to the assessment scope. See [authorization records](authorization-records.md). A separate reviewer is supported; self-review is permitted only for a sole active client member after explicit acknowledgement and rationale, recorded as `AUTHORIZATION_SELF_REVIEWED`. Neither path verifies that an authorization document is genuine; operators must verify the source document and rules of engagement outside APISentinel. Server setting `APISENTINEL_ALLOW_ACTIVE_TESTS` must also be explicitly enabled; it defaults to false and disabled runs are persisted as `SKIPPED` without sending a request. Execution accepts only assessment ID, endpoint ID, the existing legacy category field, and the fixed `HTTP_REQUEST` mode. The request URL is built server-side from the first host in the assessment scope and the endpoint path; callers cannot submit URLs, methods, headers, policy overrides, or credentials. Only GET, HEAD, and OPTIONS can be sent. Client request bodies cannot choose a URL, method, headers, policy, or credential profile. An endpoint declared as authenticated may use its assessment-bound bearer profile for transport-only requests; registered checks that require no authentication are blocked on such endpoints.

The request outcome contract is persisted on `TestRun.status`: `BLOCKED_SCOPE`, `BLOCKED_DESTINATION`, `AUTH_UNAVAILABLE`, `COMPLETED`, `OVERSIZED_RESPONSE`, `TIMEOUT`, `TRANSPORT_ERROR`, and `CANCELLED`; pre-execution records can also be `SKIPPED`, while active requests are `Running`. `COMPLETED` means the HTTP response stream was completely read within the runner contract; it does not mean a vulnerability test passed. Incomplete stream errors are `TRANSPORT_ERROR` and never completed responses. Response bodies are discarded after transport and only safe response headers, status, byte count, duration, endpoint ID, method, mode, and outcome are stored. Start, finish and endpoint-approval events are appended to `execution_audit_events`; this table is not exposed through analyst mutation routes. Legacy TestRun rows are preserved with `LEGACY` execution mode and unchanged status.

Transport execution coverage is reported separately from the existing endpoint × vulnerability-category coverage matrix. Only the latest endpoint-linked `HTTP_REQUEST` outcome of `COMPLETED` contributes to transport completion. Blocked, skipped, timed-out, failed, cancelled, oversized, running and incomplete outcomes do not contribute. The legacy vulnerability category matrix does not count HTTP request completion as a passed check.

The API request is synchronous and subject to runner connect/read/write/pool timeouts and response limits. A database partial unique index permits only one `RUNNING` HTTP request for an assessment endpoint at a time; competing starts receive HTTP 409 before any second request is sent. The endpoint is freed when the first run reaches a terminal outcome. Cancellation is not exposed in this API phase; a process interruption can leave a `RUNNING` TestRun and start audit event without a finish event. A later request recovers rows whose start time exceeds the configured overall deadline plus connection/read grace, records `HTTP_REQUEST_RECOVERED`, and keeps the prior outcome as a transport error. Rows with missing start provenance remain blocked for operator review. Rate and concurrency limits use database-backed reservations shared by workers using the same database. The database partial unique index separately coordinates the one-running-request-per-endpoint rule. A crash between outbound transmission and final database commit can also leave a `RUNNING` row; operators must not interpret it as a clean result. Audit events are append-only by application contract only; database administrators can still alter them. The authorization reference still does not independently prove client permission.

Bearer profiles and authenticator TOTP seeds use the configured secret provider. Development may use Fernet (`APISENTINEL_CREDENTIAL_ENCRYPTION_KEY`). Staging/production require AWS KMS envelope mode (`APISENTINEL_CREDENTIAL_ENCRYPTION_PROVIDER=aws_kms`) with a workload identity, key ID and region. Each secret is encrypted with an AES-256-GCM data key generated by KMS, and purpose-specific encryption context binds credential and TOTP uses. Bearer profiles are bound to one assessment. Only the owner or an analyst member can configure or revoke the profile; the runner resolves it server-side and returns only status metadata. Invalid, missing, revoked, wrong-owner or undecryptable profiles fail closed as `AUTH_UNAVAILABLE`. TOTP secrets are shown only during enrollment, required on subsequent password sign-ins, protected against same-counter replay, and never returned by status APIs. Ten 96-bit one-time recovery codes are displayed once, stored as hashes, consumed atomically during login, and audited. Rotation re-encrypts bearer profiles and TOTP seeds transactionally. AWS KMS API behavior is mock-tested here; a live KMS key/IAM/workload-identity round-trip is not available in this environment. Zero-downtime rotation is unsupported.

Evidence masking handles common credential key names recursively. It does not guarantee removal of secrets embedded in arbitrary text, URLs, or binary content. Authorization PDFs are size-bounded, hashed and discarded; the digest and filename are audited and displayed to the separate reviewer. Production authorization cannot be recorded/activated without this fingerprint. The digest establishes later file consistency, not signer identity or legal authenticity; the operator must verify authority outside APISentinel. Audit retention/deletion workflow, stronger external audit integrity and host/VPC egress firewalls remain outstanding.

Assessments identify `WEB_API`, `ANDROID_API`, or `BOTH` platform scope. APK upload is bounded to 20 MiB and forwarded to a separate non-root parser container with a 192 MiB memory limit, 0.5 CPU, 32-process cap, read-only root, dropped capabilities and no external network route. The parser never extracts archive paths or executes APK content; it reads only a bounded `AndroidManifest.xml`, validates ZIP path/entry/expansion limits, and returns package/version/SDK metadata. The API stores a SHA-256 and sanitized metadata, not the APK bytes. Parser-sidecar source is untrusted input and parser isolation is container/network isolation, not a separate VM or hardened kernel boundary. Certificate-pinning observations and device/app traffic provenance are not inferred. Structured Burp history can inventory captured endpoints, but does not prove they came from a particular APK. Android endpoints still use the same shared authorization/scope gate and HTTP runner.

`APISENTINEL_RUNNER_EGRESS_ALLOWED_CIDRS` adds an application-layer outbound allowlist after DNS resolution and before pinned connection. Every DNS answer and each redirect hop must fit an allowed CIDR in addition to passing the existing global-address prohibition and scope rules. Staging/production require this setting and reject default routes. This does not replace host/VPC firewall rules; those must separately confine the API container and permit only approved destination CIDRs, DNS, private parser traffic and the managed KMS endpoint. See [deployment egress policy](deployment-egress.md).
