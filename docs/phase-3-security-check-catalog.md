# Phase 3 security check catalog

Taxonomy: [OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/). Ten registered checks cover narrow read-only observations in API1–API5 and API8. API9 has a passive, persisted inventory review. API6, API7, and API10 remain manual or uncovered; no category is treated as fully tested.

All checks share `TestDefinition`, the same registry, endpoint model, execution route, authorization/scope validation, and bounded `runner.run_request` boundary. Applicability to `WEB_API`, `ANDROID_API`, or `BOTH` denotes compatible server-side endpoint input, not proof of browser or Android device behavior. All are disabled/enabled by the server-side `APISENTINEL_ENABLED_SECURITY_TESTS` allowlist; active transport additionally requires reviewed endpoint authorization and `APISENTINEL_ALLOW_ACTIVE_TESTS=true`. Default configuration enables the Content-Type and HSTS checks plus API1, API2, API3, API4, and API5 bounded checks. CORS, cookie, and verbose-error checks remain disabled by default. All active HTTP requests still require `APISENTINEL_ALLOW_ACTIVE_TESTS=true`.

API9's **Review current inventory** action creates an immutable database snapshot of imported operations. It flags unreviewed, deprecated, stale, versionless, duplicated, and import-warning records. It sends no requests and cannot establish completeness without a client-provided source of truth.

## Result semantics

`TestRun.status` remains the transport lifecycle/outcome for compatibility. `security_outcome` retains the detailed legacy check contract (`NOT_RUN`, `INCONCLUSIVE`, `NO_ISSUE_OBSERVED`, `CANDIDATE_FOUND`, `ERROR`). New `execution_classification` provides the compact UI/API state:

| Classification | Meaning |
|---|---|
| PASS | This narrow configured observation did not identify its expected mismatch. It does not certify the endpoint. |
| FAIL | A configured mismatch produced an unconfirmed candidate finding. Analyst review is required. |
| INCONCLUSIVE | Available evidence did not support a safe conclusion. |
| ERROR | Transport or check evaluation failed. |
| NOT_APPLICABLE | No registered check was evaluated for the run, or the check was not applicable. |
| BLOCKED | Authorization, scope, destination, credentials, active-test policy, or cancellation prevented evaluation. |

Confidence is separate from severity and finding status. Check-generated candidates use the existing Informational severity and low-confidence analyst-review text. Severity does not change automatically when the check runs.

## Deliberately unsupported without explicit fixtures

No credential guessing, token forgery, login/logout mutation, role escalation, injection payloads, property mutation, bulk enumeration, repeated rate-limit probing, SSRF callback, payment/workflow mutation, or APK runtime/device/pinning claim is enabled. BOLA and BFLA cover only the explicit two-identity, one-endpoint read-only comparisons above; they do not establish route-wide behavior. API1/API2/API3/API4/API5 checks are enabled in the default registry but cannot send requests until `APISENTINEL_ALLOW_ACTIVE_TESTS=true` and all assessment scope/authorization gates pass. CORS, cookie, and verbose-error checks remain disabled unless an operator adds their IDs to `APISENTINEL_ENABLED_SECURITY_TESTS`.
