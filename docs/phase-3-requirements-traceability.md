## Baseline audit

- Stack: Python 3.13 in the local runtime (project supports Python >=3.11), FastAPI, SQLAlchemy 2, Alembic, HTTPX 0.28.1/httpcore 1.0.9, Pydantic, React/TypeScript/Vite, pytest. No dependency changes were needed; migration 0030 adds persisted API9 inventory-review snapshots and migration 0031 adds encrypted assessment-bound test identity profiles.
- Existing architecture: `src/apisentinel/test_registry.py`, `runner.py`, `safety.py`, `authorization.py`, `job_queue.py`, and `api.py` already provide a single typed registry, bounded scope-aware runner, DNS/IP and redirect validation, reviewed authorization, cancellation, lifecycle/audit, evidence-linked findings/retests, and coverage/report integration. `collection_import.py` normalizes Web and supplied Android traffic into the shared endpoint model; APK manifest metadata remains a separate, isolated parser feature.
- The registry has five API8 observations, one API1 synthetic-object comparison, one API2 unauthenticated probe, one API3 property-name heuristic, one API4 single-response quota-header observation, and one API5 approved-role comparison. BOLA/BFLA require two encrypted client-provisioned identities and send only bounded GET requests; API9 inventory review analyzes imported records only.
- Baseline: `pytest -q` -> **107 passed, 1 skipped**, one Starlette/httpx deprecation warning. The skipped test is environment-gated PostgreSQL validation; the baseline did not fail.
- Migrations 0030 and 0031 are additive; legacy result fields and API shapes remain, with additive check metadata, API9 review routes, and assessment-bound test identity profiles.

## Security boundaries

- This implementation change did not contact a target. Historical verification records below refer to earlier repository states and do not cover the API1–API5/API9 additions.
- Security checks remain behind authentication, client/assessment access, reviewed authorization, approved endpoint status, server allowlist, `APISENTINEL_ALLOW_ACTIVE_TESTS`, bounded runner, and destination/scope checks.
- A `FAIL` execution class means the check's configured observation did not meet its expected property; it creates only a `Candidate` finding. It is not a confirmed vulnerability or severity rating.
- Categories with zero registered checks are uncovered, never passed. Check results do not establish the absence of vulnerabilities.


The prior test results in this traceability record predate the expanded read-only registry and migrations 0030–0031; no test or frontend build was run for those additions in this task.
